# 01 · 多智能体科研流水线架构设计（MARS-8H）

> 这份文档解释**为什么这么设计**。考场来不及想原理，但被评委问到"你这套东西跟直接问 ChatGPT 有什么区别"时，你需要能答上来。答得好是加分项。

---

## 1. 一句话架构

**MARS-8H = 指令层（Conductor）+ 情报层（5 视角侦察 + 交叉质询）+ 方案层（3 方案 + 红队剪枝）+ 执行层（Coder/Runner/Monitor/Fixer 闭环）+ 交付层（Evaluator/Writer/QA）**，角色之间**只通过磁盘文件通信**，用**门控（G0–G5）**串起来，用**时间盒**约束。

```
                        ┌──────────────── Conductor（唯一决策者）
                        │  持有：Task Ledger + Progress Ledger + 时间预算
                        │  输出：[STATE] 行，不输出长文本
                        └───┬───────────┬───────────┬───────────┬──────────┐
                     G0 任务     G1 情报      G2 方案      G3-4 执行    G5 交付
                            │           │           │           │          │
                    ┌───────▼──┐  ┌─────▼─────┐ ┌───▼────┐ ┌────▼─────┐ ┌──▼────┐
                    │ 5 Scout  │→ │Synthesizer│→│Architect│→│  Coder   │→│Writer │
                    │ TASK     │  │ 矛盾裁决   │ │ ×3 方案 │ │ Runner   │ │ QA    │
                    │ DATA     │  │ 未知登记   │ │RedTeam  │ │ Monitor  │ │Eval   │
                    │ METHOD   │  │ Brief     │ │Chair    │ │ Fixer(×3)│ │       │
                    │ METRIC   │  └───────────┘ │Spec     │ └──────────┘ └───────┘
                    │ RISK     │                └────────┘
                    └──────────┘
                    并行 15 min    8 min        15 min      主体时间

  通信介质：runs/ 目录下的文件（黑板）——不是对话历史
  每个角色输入：文件路径 + 一句话目标   输出：指定路径的文件 + ≤40 字结论
```

## 2. 为什么要分这几层（对齐当前最强系统）

### 2.1 情报层：视角化检索 + 交叉质询（来自 STORM）

STORM（[arXiv:2402.14207](https://arxiv.org/abs/2402.14207)）的核心发现：写高质量长文的关键不在"写"，而在**先用多个不同视角去提问，再模拟对话把答案逼出来**。它把流程拆成「视角发现 → 模拟对话（提问者/专家）→ 大纲 → 正文 → 润色」。

映射到实训：**5 个 Scout 就是 5 个视角**，而且必须是**不同角色**在问，不是同一个 Agent 连问五次。原因很实际——同一个 Agent 连问五次，第 2–5 次的检索词会高度重复，你拿到的是同一批网页的五种说法。换成 5 个不同视角（任务/数据/方法/指标/风险），检索词的分布会显著发散。

**Synthesizer 的"矛盾裁决表"是这一步的真正价值**。多 Agent 系统最常见的失败是"五个 Agent 说了五套，主控挑一个听起来最顺的"。P3 强制要求把它们之间的矛盾**显式列出来并给出裁决方式**，这就把"信息"变成了"可用信息"。

### 2.2 方案层：树搜索 + 评审剪枝（来自 AI Scientist-v2）

AI Scientist-v2（[arXiv:2504.08066](https://export.arxiv.org/abs/2504.08066)）把科研自动化做成**渐进式 agentic tree search**：不是线性走 idea → 实验 → 写稿，而是并行展开多个节点，用评审反馈剪枝，配合 VLM 对图表做反馈闭环。

映射到实训：**3 个风险偏好不同的方案（SAFE / SOTA / GREEDY）就是三个搜索节点**，红队（3 个视角的评审）就是剪枝函数。关键设计是**评分公式带权重**：

```
score = 0.30×时限内跑通概率 + 0.25×得分上限 + 0.15×实现简单度
      + 0.15×可回滚性 + 0.15×不被判定违规
```

这个公式里"时限内跑通概率"权重最高，是刻意的：**实训不是论文投稿，交不出东西就是 0 分**。纯 SOTA 追求会被这个公式自动压掉。

### 2.3 执行层：双层账本 + 停滞检测（来自 Magentic-One）

Magentic-One（[arXiv:2411.04468](https://ar5iv.labs.arxiv.org/html/2411.04468v1)）的 Orchestrator 维护两本账：
- **Task Ledger**：事实、猜测、计划（"我们知道的"和"我们打算做的"）
- **Progress Ledger**：本轮谁做了什么、是否在推进、是否需要重规划

并且它有一个**外层循环**：内层循环推进任务，一旦检测到"停滞"（连续若干轮没有实质进展）就跳出内层、重新规划。

映射到实训：`runs/00_task.md` + `runs/40_progress.md` 就是这两本账。P8 里的 `verdict=RUNNING|STALL|DIVERGE|OOM|DONE|DEAD` 就是停滞检测的六种状态。**这一步很多人不做，结果是训练挂了 40 分钟才发现。**

### 2.4 编排层：orchestrator-worker 的四条工程教训（来自 Anthropic）

Anthropic 公开的多智能体研究系统经验里有几条直接可用的结论（[原文](https://www.anthropic.com/engineering/multi-agent-research-system)）：

| 结论 | 在实训里的落地 |
|---|---|
| orchestrator-worker 在广度优先的信息检索任务上，比单 Agent 有明显提升 | 情报层必须并行 fan-out，不要串行 |
| **子任务的描述质量决定成败**——含糊的委派会产生重复劳动 | 所以 P2 强制"视角定义 + 输出 schema + 字数上限"，不给自由发挥空间 |
| 多 Agent 的 token 消耗远高于单 Agent（约一个数量级） | 所以每个角色都有字数上限（卡片 800 字、Brief 1200 字），超了就落盘、只回结论 |
| 必须评估**轨迹**而不只是最终答案 | 所以 P8/P10 要求 `40_progress.md` 和 `45_boost.md` 留痕，答辩时这就是"你的科研过程" |

## 3. 黑板协议（Blackboard Protocol）

**这是整套架构能跑起来的技术前提**：角色之间**不共享上下文，只共享文件**。理由有三条，都是实践踩出来的：

1. **上下文爆炸**：5 张卡片 + Brief + 3 方案 + 代码 + 日志，全塞进一个上下文，模型在第 3 小时后会开始遗忘早期约束（题面要求、路径、指标定义）。
2. **结论污染**：Agent A 的猜测进入 Agent B 的上下文后会被当成事实复述，两轮之后没人记得它原本是猜测。
3. **可恢复性**：上下文是易失的，文件不是。断线、换模型、重启会话，只要 `runs/` 在，就能从任意 gate 续跑。

### 目录与工件

```
runs/
├── 00_MISSION.md      任务书（F1 建立）
├── 00_task.md         任务契约（G0，P1）—— 唯一事实来源，后面所有角色都读它
├── 01_env.md          依赖白名单（G0.5，P1.5）
├── 05_rubric.md       评分模型（P13 前置，F3）
├── 10_cards/          情报卡（G1，P2）每个视角一个文件
│   ├── TASK.md  DATA.md  METHOD.md  METRIC.md  RISK.md
├── 10_brief.md        情报简报（G1 收口，P3）
├── 20_candidates.md   三方案（G2，P4）
├── 25_decision.md     决策矩阵（G2，P5）末行 DECISION: ...
├── 30_spec.json       实验规格（G2 收口，P6）—— 机器可读，编排器读这个
├── 30_spec.md         实验规格（人可读，含启动命令）
├── 40_progress.md     进度账本（P8 每次轮询追加一行）
├── 45_boost.md        提分台账（P10，含"已验证无效"的记录）
├── 50_logs/           smoke.log / main.log / error.log
├── 60_metrics.json    指标（G4，P11）—— 唯一允许被引用的数字来源
├── 61_eval.log        评测原始输出（两次复现，证明可复现）
├── 70_ckpt/           best.pt / last.pt / e{N}.pt
├── 90_submission/     提交目录（内容与题面逐字对齐）
├── 95_qa.md           验收报告（G5）
└── BLOCKED.md         阻塞记录（降级时写）
```

### 消息最小 schema

任何角色回给 Conductor 的消息，**只有两种形态**：

```json
{"artifact": "runs/10_cards/METHOD.md", "conclusion": "≤40字", "confidence": 0.7, "next": "建议下一步或null"}
```

```json
{"error": "一句话根因", "need": "需要的资源或决策", "fallback_used": "D2"}
```

**禁止**：角色回一段 500 字的分析。超了就落盘，只回路径。这条规则在 P0 里已经写死，是所有角色提示词的第一约束。

## 4. 门控与时间盒

### 时间分配（P0 里的比例，会自动换算成本次的具体分钟）

| 阶段 | 占总时长 | 480 分钟时 | 硬判据（不满足就不许进下一阶段） |
|---|---|---|---|
| G0 任务契约 | 0–8% | 0–38 min | `00_task.md` 里 outputs 逐字抄完，metric 有定义 |
| G1 情报 | 8–20% | 38–96 min | ≥3 张卡 + Brief 里有"不知道什么" |
| G2 方案 | 20–30% | 96–144 min | `30_spec.json` 通过 5 条自检 |
| G3 baseline | 30–45% | 144–216 min | `--mode smoke` 退出码 0，且主训已启动有 pid |
| G4 主实验 | 45–80% | 216–384 min | `60_metrics.json` 有合法数字 |
| G5 交付 | 80–95% | 384–456 min | `QA_RESULT: PASS` |
| 冻结 | 95–100% | 456–480 min | 只读，不写 |

**为什么 G3 要占 15%？** 因为 baseline 跑通是整场考试的分水岭。它之前你一无所有，它之后你有一个可以不断改进的、已经能交的答案。绝大多数翻车都发生在"跳过 baseline 直接上大招"。

### 门控的物理含义

门控不是流程装饰，每一道都对应一种真实的失败：

- **G0 不做** → 写完了才发现提交格式是 csv 不是 json。
- **G1 不做** → 选了一个 8 小时跑不完的方法。
- **G2 不做** → 三个小时在改一个根本不涨点的方向。
- **G3 不做** → 训练启动 40 分钟后发现 dataloader 死锁。
- **G4 不做** → 有分数但不知道分数怎么来的，答辩问一句就露。
- **G5 不做** → 分数不错，但文件名大小写错，判 0。

## 5. 三个失败模式与对策

| 失败模式 | 症状 | 架构层对策 | 对应提示词 |
|---|---|---|---|
| **上下文爆炸** | 3 小时后 Agent 忘记题面要求，重复做已完成的事 | 文件通信 + 字数上限 + `[STATE]` 行 | P0, F2 |
| **结论同质化** | 5 个 Agent 说出同一句话，检索白做 | 5 个**不同视角**而非 5 个同题 Agent；强制"死路"字段 | P2, P3 |
| **幻觉指标** | README 写 0.87，日志里是 0.79 | `60_metrics.json` 为唯一数字来源 + grep 校验 | P11, P12, P13 |
| **单点僵死** | 一个报错改 1 小时 | Fixer 配额 3 次，用完强制降级 | P9, P14 |
| **训练插队** | 同时跑 3 个实验，显存爆，都不出结果 | 一次一个变量 + 串行 + 显存估算字段 | P6, P10 |

## 6. 落地矩阵：三种现场条件怎么实现同一套架构

| 现场条件 | 实现方式 | 用哪份提示词 | 并行度 | 可靠性 |
|---|---|---|---|---|
| CLI Agent 有 subagent/workflow 工具（Codex / DSH / Claude Code） | **原生 fan-out** | F1 + F2 + P 系列 | 高（真并行） | ★★★★ |
| 只有一个 OpenAI 兼容 API（DeepSeek 等），无 Agent 工具 | **Python 编排器**（`tools/orchestrator-mars.py`） | 编排器内置角色提示词 | 中（线程池并发） | ★★★★ |
| 模型也不通，只有 SSH 和一个编辑器 | **人工流程卡** | F4 + P2.5 + P13 | 无 | ★★★（能及格） |
| 有 Web UI 的对话框 | **单会话角色扮演**（每次切换前声明 `[ROLE] xxx`） | P0 → P1 → P2×5 → P3…… | 无（串行） | ★★★ |

**关键**：四种方式的**工件格式完全一致**（都是 `runs/` 那套）。所以现场条件变化时可以中途换实现方式，已产出的卡片和 brief 都能继续用。这是刻意的设计——考场最怕的是"方案 A 挂了，方案 B 要从头来"。

## 7. 这套架构为什么在实训里能加分（不只提分）

实训评分通常不只指标。以下几点是这套流水线**顺手就产出**的，而手写代码的人往往要额外花时间补：

1. **可复现性**：`61_eval.log` 里有两次同结果评测 → 直接证明没调参作弊。
2. **消融表**：`45_boost.md` 天然就是消融实验记录（改动/before/after/Δ）。
3. **失败尝试**：`BLOCKED.md` 和 `45_boost.md` 里"已验证无效"的行 → README 第 5 段的素材，评委很吃这套。
4. **工程规范**：`--mode smoke`、结构化日志、配置外置、异常处理 → 代码质量分。
5. **过程留痕**：`40_progress.md` 的每分钟状态行 → 被问"你时间怎么分配的"时有据可查。

**答辩话术（背下来）**：

> "我没有直接让模型写代码。我先用五个不同视角的检索角色把任务、数据、方法、指标、风险分别摸清并做了矛盾裁决，然后用三个风险偏好不同的方案做决策矩阵，选定主线并绑定了切换条件。执行阶段一次只改一个变量，所有指标只从 `metrics.json` 出。所以我能说清每一个点的来源和代价。"

## 8. 与"直接问 ChatGPT"的本质区别

| 维度 | 直接对话 | MARS-8H |
|---|---|---|
| 信息 | 一次检索，容易撞到同一个网页 | 5 视角并行 + 矛盾裁决 |
| 决策 | 模型随口推荐一个方法 | 加权矩阵 + 显式切换条件 |
| 执行 | 一次生成 400 行代码，报错就重生成 | 契约化代码 + smoke 门 + 单变量修错 |
| 监控 | 盯着终端看 | 结构化日志 + 六态判定 + ETA |
| 交付 | 最后 30 分钟手忙脚乱 | 80% 时间点就有可提交版本 |
| 可解释 | "模型说这样好" | 每一分都有账本 |
