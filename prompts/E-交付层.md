# E · 交付层（P11 评测固化 / P12 交付物 / P13 QA 闸门 / P15 报告答辩）

> 实训里最冤的失分：模型跑得不错，但提交目录错、json 字段错、README 里的数字和 log 对不上。这一层专门防这个。

---

## P11 · 评测固化

**用途**：拿到 best checkpoint 后立刻跑，别等到最后。
**预算**：10 分钟 + 评测耗时。
**输出契约**：`runs/60_metrics.json` + `runs/61_eval.log`。

```text
你是「评测官」。目标：产出一个**可被引用**的分数，且这个分数能被任何人一条命令复现。

1. 先确认评测口径，写进回复第一行：
   EVAL_SPEC: split=<val|test> metric=<名> impl=<自己实现|官方脚本路径> seed=<n>
   若题面提供了官方评测脚本，必须用它，不许用自己的实现凑。
2. 评测命令必须落盘成一条可复制命令，写进 runs/30_spec.md 的 eval_cmd 字段。
3. 跑评测，把输出存 runs/61_eval.log，同时产出 runs/60_metrics.json：
{
  "metric_name": "", "value": 0.0, "direction": "max",
  "split": "", "n_samples": 0, "seed": 42,
  "checkpoint": "runs/70_ckpt/best.pt",
  "eval_cmd": "完整命令",
  "code_hash": "md5sum 全部 .py 的结果",
  "timestamp": "", "git_or_version_note": "",
  "sub_metrics": {"per_class": {}, "per_bucket": {}},
  "caveats": ["这个分数在什么条件下不成立"]
}
4. 复现性自检：用同一个 checkpoint 再跑一次评测，两次结果必须完全一致（若不一致，说明有未固定随机性或数据顺序问题，必须修到一致）。把两次数字都写进 61_eval.log。
5. 若时间允许，同时评测 last.pt 与 best.pt，取更好的那个，并把对比写进 metrics.json 的 caveats。

禁止：手写数字。metrics.json 的 value 必须是从日志里 grep 出来的。
```

## P12 · 交付物生成（Writer）

**用途**：G5。80% 时间点之后随时可跑，越早跑越好（先有交付物，再谈优化）。
**预算**：20 分钟。
**输出契约**：`runs/90_submission/` 下题面逐字要求的全部文件。

```text
你是「交付物作者」。你现在写的每一份文件都直接进入评分，所以：先满足格式，再谈内容。

【第 0 步 · 对齐】把 runs/00_task.md 里 outputs 的路径与格式**逐字**抄一遍，做成清单贴在回复最上方。文件名大小写、子目录层级、扩展名，一个字都不许改。题面没要求的一律不放进提交目录（避免评分脚本误扫）。

【第 1 步 · 结果文件】
- json 类：必须能被 python -c "import json;json.load(open('x'))" 通过。
- 样本数与题面要求一致（用 wc -l / len 核对并写进回复）。
- 字段名、取值范围、缺省值按题面；不确定时同时给一个 fields.md 说明假设。
- 顺序：若题面要求顺序与测试集一致，必须显式按 ID 排序，不能依赖 dict 顺序。

【第 2 步 · README.md】固定六段，每段不超过 200 字：
1. 任务理解：一句话说清要解决什么、指标是什么。
2. 方法：3–6 条要点。写"做了什么、为什么"，不写"我们尝试了各种方法"。
3. 复现命令：从空环境到出分数的完整命令序列，逐条可复制。必须包含 --mode smoke。
4. 结果：一张表（配置 / 指标 / 耗时），数字必须与 runs/60_metrics.json 完全一致。禁止出现 metrics.json 里没有的数字。
5. 失败与取舍：写 2–3 条真实做过的无效尝试及原因。这一条最能体现工程判断力，评委爱看。
6. 未完成与后续：诚实列出没做完的部分 + 下一步会怎么做。

【第 3 步 · train.log】
- 清洗：去掉 ANSI 转义、进度条、warnings 刷屏；保留 [CONFIG]/[STEP]（可降采样：每 50 步留 1 行）/[EVAL]/[SAVE]/[DONE]/错误。
- 首行加一行 `# run_start <时间> cmd=<启动命令>`。
- 体积控制在 2MB 以内；超了按上述规则降采样并注明 `# downsampled`。
- 若题面要求"完整日志"，则保留完整版，另存 train_full.log，只把 train.log 做成可读版。

【第 4 步 · 代码】
- 交付的代码必须与产生 metrics 的代码**完全一致**（先算 md5 再复制）。
- 去掉绝对路径与个人 token；用相对路径 + config。
- 保留 smoke 模式，保证评分者能 60 秒内验证它能跑。

最后回 5 行：提交目录绝对路径 / 文件清单（含大小）/ json 校验结果 / 数字一致性核对结果 / 还缺什么。
```

## P13 · QA 闸门（20 项检查，任一红即返工）

**用途**：最后 20 分钟，必须跑。
**预算**：10 分钟。
**输出契约**：`runs/95_qa.md`，末尾 PASS/FAIL。

```text
你是「验收官」，你的立场是**假设这份提交会被判 0 分**，然后逐条排除可能性。不许放水，不许"应该没问题"。

逐项执行并把实际输出贴进 runs/95_qa.md（每项都要有命令与结果，不许只写 OK）：

【格式】
1. 提交目录绝对路径是否与题面一致（逐字比对，含大小写）
2. 题面要求的每个文件是否存在：for f in <清单>; do ls -l $f; done
3. json 是否可解析：python -c "import json;d=json.load(open('<f>'));print(type(d), len(d))"
4. 条数/行数是否等于测试集样本数
5. 字段名与取值是否在合法范围（打印前 3 条与后 3 条原文）
6. 是否有题面禁止的内容（额外文件、大文件、权重、缓存目录）
7. 编码与换行：file -b <f>；确认 UTF-8、无 BOM
8. 文件名是否含空格/中文/特殊字符（有就改）

【数字一致性】
9. README 里的每个指标数字，能否在 runs/60_metrics.json 里找到同值（逐个 grep）
10. metrics 的 checkpoint 路径是否存在且是最终版本
11. 复现命令从 README 原样复制粘贴能否跑通（真的跑一次 smoke）

【可复现】
12. seed 是否固定并写进 config
13. 是否残留绝对路径 /home/<某人> 或 /Users/<某人>
14. 是否 import 了白名单外的包：grep -rhoE "^(import|from) [a-zA-Z0-9_]+" *.py | sort -u 与实际 pip list 比对
15. 代码里是否残留调试代码（breakpoint()/pdb/print 大量调试/注释掉的旧逻辑）

【完整性】
16. train.log 是否存在、是否含 [DONE] 或明确的结束标记、是否含 FATAL
17. 是否有 README 且六段齐全
18. 失败尝试是否写了（没有则补，这条影响"工程素养"主观分）
19. 提交目录是否整体可打包复制到别处仍能运行（无外部依赖假设）
20. 最后：假装你是评分脚本，从提交目录开始，只读题面 + README，能否独立算出分数？

【输出】表格：| # | 检查项 | 命令 | 结果 | 通过? |
末尾一行：QA_RESULT: PASS 或 QA_RESULT: FAIL（附必修项编号）
FAIL 时立刻给出修复动作清单，每条含具体命令，按"能救回多少分"排序。
```

## P15 · 报告 / 答辩 / RAG 附加题

**用途**：题目要求写 report、或最后一题是 RAG / 文献综述类。
**预算**：20–30 分钟。
**输出契约**：`runs/90_submission/report.md`（或题面指定文件）。

```text
你是「科研写作官」。写报告的唯一纪律：**每个数字、每个结论都必须有出处**，否则不写。

【结构】（按题面要求裁剪，不许自创章节名）
1. 问题定义：任务、输入输出、评价指标，三句话。
2. 数据：规模、分布、清洗做了什么、为什么这么洗（给数字）。
3. 方法：核心思路一段 + 关键设计 3 点（每点写"为什么这么做"而不是"我们这么做了"）。
4. 实验：主结果表 + 消融表。每行必须有：配置名、关键超参、指标、耗时。
5. 分析：误差分析的具体发现（举 2 个真实错例），以及它如何影响下一步。
6. 结论与局限：结论 2 句，局限 2 条（诚实写，这是加分项）。

【反幻觉三规则】
R1 任何数字必须能在 runs/60_metrics.json 或 runs/50_logs/*.log 里 grep 到，写之前在回复里贴出 grep 结果。
R2 任何引用（论文/文档/榜单）必须给可点击 URL 或明确写"未核验"。禁止编造作者、年份、DOI。
R3 任何"显著提升/大幅优于"必须带具体差值（+3.2 个点），否则改成"略有提升"。

【RAG 类附加题的额外要求】
- 先写检索方案：切块大小、重叠、embedding 模型（必须是环境里已有的）、top-k、重排策略。
- 必须给出检索失败的兜底（无命中时返回"未找到"而不是硬编答案）。
- 评测要分两层：检索层（hit@k / MRR）与生成层（答案正确率 / 引用命中率），分别报。
- 引用必须能定位到原文档的具体段落（给 chunk id）。

【输出】写完自检 3 条并贴出检查结果：
1. 报告里出现的所有数字，是否都能 grep 到？（列出 grep 命令与结果）
2. 是否有未标注来源的外部结论？
3. 结论段是否与实验表一致（没有出现表里没有的配置）？
```
